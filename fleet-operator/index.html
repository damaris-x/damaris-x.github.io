carafe / always-on Macs for AI agents

Declare your Macs. Kubernetes keeps them.

The carafe Fleet operator runs Fleet, the open-source device manager from FleetDM, inside your cluster. Through Fleet it checks that every Mac station is awake, logged in and running its AI agent (Claude Code, Codex or your own), and runs the configured fix when a check fails.

Where it sits

Five layers of AI. carafe is layer 3, the infrastructure.

Jensen Huang describes AI as a five-layer stack: energy, chips, infrastructure, models and applications. Infrastructure includes power delivery, networking and the systems that run many processors as one machine. carafe is building that layer for AI agents: a Mac mini cloud that keeps each agent's machine powered, connected and running.

Framework from Jensen Huang, "AI Is a 5-Layer Cake", NVIDIA blog, 2026-03-10. Placing carafe on it is our reading; carafe is not affiliated with or endorsed by NVIDIA.

The problem

An AI colleague only works while its computer is on.

Lid closes

The agent stops.

Claude Code, Codex and other agents run on someone's laptop. Remote access helps, but only while that laptop is awake. Not everyone can keep a computer on, or set one up.

Real work is in a browser

A container has no browser.

Permit applications on government portals and design proposals happen in web pages. Claude in Chrome drives a real Chrome on a real desktop, so the plan is a Mac mini for each of them.

Now there are N Macs

Someone has to keep them alive.

Every station must stay awake, logged in, with the agent and its browser running, and be fixed from afar when it is not. Doing that by hand in a device console adds one more place for settings to drift.

First use / carafe, for Claude Code

One always-on Claude workspace per colleague, reachable from the phone.

A carafe is one person's own container with Claude Code, their work folder and the company's skills. A Mac station runs the same setup natively on a Mac mini, with a real Chrome. Each has one web page, the cellar door, where the person signs in and turns on phone access. Then they work from the Claude app.

  • A session started from claude.ai/code, the same path the phone uses, drove Chrome on a Mac station. After a reboot the station came back by itself in about two minutes. A test on a real phone is still to come.
  • The Fleet operator reports every station's checks and runs the configured fix when one fails.

Two rules from the start

Everyone signs in themselves.
The sign-in happens in the person's own browser, through Anthropic's flow, and the code goes straight into their own carafe. carafe keeps no copy of anyone's Claude credentials.
Claude's questions are the person's to answer.
"Trust this folder?" and "Enable Remote Control?" are shown verbatim and answered by the person. carafe never answers them for anyone.
The operator respects that line.
The signed-in check has no remedy. Signing in again needs the person, so the operator reports it and stops there.

How it works

One operator. Three resources. One writer.

The operator owns Fleet: it deploys it, sets it up, configures it and upgrades it. Fleet in turn manages the Macs. The operator is meant to be the only thing that writes to Fleet.

FleetServer — one per company
Fleet, MySQL and Valkey from the official Helm chart: spec.version picks Fleet, spec.chartVersion the chart. Then TLS, the first admin, an API user, Secrets, NodePort and NetworkPolicies.
FleetConfig — one per company
Policies, scripts and labels, kept matching the spec: removed from the spec means removed from Fleet. Built-in and person labels are left alone.
MacStation — one per person
An enrolled Mac, found by serial number: labelled with its person, every check in status, and the remedy script run when a check fails.

What you write

A health check and its fix, declared in YAML.

Each policy is an osquery check that runs on every Mac. Give it a remedy and the operator runs that script when the check fails and the Mac is online. Give it none and the operator only reports.

  • Five station checks ship in the example: never sleeps, logs in by itself, the agent page answers, Chrome is running, Claude is signed in.
  • kubectl get macstations shows every person's Mac, with the five station checks as columns.
  • Hand edits are reverted at the next drift check.

Any agent

Claude Code, Codex or your own agent.

If it runs on macOS, the operator can watch it. A check is an osquery query, a fix is a shell script run as root, and both live in your spec. Anything osquery can see counts: a process, a launchd job, a port, a heartbeat file.

Configuration drift

The spec is the only truth. Hand edits are put back.

No edits in Fleet's web page, no separate GitOps run, no tug of war between two tools. The operator reads Fleet back every five minutes and makes it match.

Self-healing

A failed check triggers its fix, carefully.

The operator runs a remedy only when four things hold. That keeps a broken script from hammering a Mac, and skips Macs that are off.

  1. The policy is failing, per Fleet's own result.
  2. The spec names a remedy for it.
  3. The Mac is online. Nothing new is sent while Fleet reports it offline.
  4. The backoff has passed since the last run.

After a reboot every check came back with nobody touching the Mac. The operator works out boot time from uptime, because in the lab a quick reboot never showed as offline in Fleet; it landed within one second of the kernel's own boot time.

Fleet Free

Runs on Fleet's free tier.

Fleet's own "run a script when a policy fails" is a Premium feature. The operator does it itself with what the free tier already has: scripts, policies, labels and an API-only user.

When we looked in October 2026 we found no Kubernetes operator for Fleet, from its maintainers or the community. The options were the Helm chart, a Terraform provider and fleetctl gitops. The operator uses the official chart rather than replacing it.

Security

The token that can run root on every Mac stays in one namespace.

  • Least privilege in Fleet. The operator's API user defaults to maintainer, the lowest role that can run scripts, not admin.
  • Least privilege in Kubernetes. A namespaced Role, never a ClusterRole. The operator watches one namespace only.
  • NetworkPolicies by default. MySQL and Valkey only from inside the namespace; from outside the cluster, only Fleet's port.
  • The AI agents' pods cannot reach Fleet. The lab found that a pod going to a node's NodePort keeps its pod address, so the rule for the Macs excludes the pod network. In the kind lab, pods in other namespaces timed out on the Service, the NodePort and MySQL. Nothing else runs in Fleet's namespace.

Multi-company

One Fleet per company, tested apart.

Each company gets its own namespace, operator, Fleet, database and port, and later its own Apple push certificate. Fleet's free tier has one organization per install, so this is also how each company sees only its own name and its own Macs.

  • <1 GB memory per company, 690–930 MB observed
  • ~20 MB the operator itself

Where it goes / a small office [direction, not built yet]

Next: an agent-ready office for a ten-person company.

A small company has no IT team and no Kubernetes. The plan: it buys a carafe box that becomes its control plane, with no data centre to rent and nothing hosted by us. An engineer sets it up, then works on the team's workflows.

carafe box — the control plane
A Raspberry Pi 5 running k3s and the operator. The company owns it and decides who is admin; support would get in only with its approval, each visit logged.
carafe — one per person
Claude Code, a work folder and the company's skills, on a host in the office, reached from the phone.
Mac station — one per boundary
A Mac mini for each role that must stay apart: front desk, finance, back office, audit, the owner. Each checked and fixed by the operator through Fleet.
network — the office's own
Claude Code's Remote Control opens no inbound ports, so phones need no public address; Fleet stays on the office LAN. A recommended UniFi kit would add a VLAN for the agents, PoE and a 5G backup line.

Setup

The box goes in.

An engineer, ours or a partner's, installs the box, sets up the network and sign-in, and gives everyone a carafe.

The engagement

Work, not plumbing.

The setup is the same in every office, so the engineer's time goes to one or two workflows for each team.

After

Skills travel.

Those workflows become skills that the next company of the same kind can start with. A subscription per person would cover monitoring, upgrades and skill updates.
